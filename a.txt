==============================================================================

WHY THIS CHANGE IS NEEDED
==============================================================================

Roman Urdu users require llama-3.3-70b-versatile because response quality from 8B is not acceptable.

However today the expensive model is performing TWO jobs:

1.
Understanding the message
Generating JSON
Planning information

2.
Writing the Roman Urdu reply.

Only the second job actually requires 70B.

Intent extraction and structured JSON generation do not require high-quality conversational Roman Urdu.

Therefore we want to split these responsibilities.

API KEY ROTATION REVIEW (CRITICAL)
==============================================================================

Please perform a full code review of the Groq API key rotation implementation.

There is a production issue that needs investigation.

Observed behavior:

When the currently active Groq API key has exhausted its quota, the backend sometimes returns an error directly to the chat/user.

Only after the user sends another message does the backend rotate to the next API key and succeed.

Expected behavior:

If one API key fails because of:

• quota exceeded
• rate limit
• exhausted credits
• temporary retryable API failure

The backend should automatically retry using the next available API key BEFORE returning any error to the frontend.

The user should never see an API quota error if another healthy API key is available.

Please investigate whether there is a bug in:

• retry logic
• rotation logic
• exception handling
• recursion/loop exit
• async handling
• request retry order

If a bug exists, fix it.

The frontend should receive an error ONLY if every configured API key has failed.
